# Capturing 802.11 frames for Airlock

The analyzer reads any pcap containing 802.11 frames. This document covers
how to produce one, and how the lab was contained.

---

## Lab setup and containment

- A spare travel router acting as the access point, on its own SSID, not
  bridged to the home network.
- Two client devices I own: a laptop and a phone.
- A capture host with a monitor-mode-capable adapter.
- The AP reconfigured between runs to produce each security generation:
  WPA2-PSK with PMF off, WPA2 with PMF optional, WPA3-SAE with PMF required,
  and WPA2/WPA3 transition mode.

Containment rules followed throughout:

1. Only my own devices and my own AP were captured.
2. The lab AP was isolated, not the household network.
3. No capture was taken in a place where other networks' traffic would be
   recorded incidentally beyond unavoidable beacon frames.
4. No deauthentication frames were transmitted at any network other than my
   own isolated lab AP, and the deauth frames in the committed sample capture
   are synthetic — generated by `wifi/synth.py`, never put on the air.
5. No captured handshake was used for passphrase recovery; the analyzer reads
   metadata only.

Capturing traffic on networks you do not own or have written authorization
to test is illegal in most jurisdictions. Keep it to your own hardware.

---

## Why monitor mode is required

A normal Wi-Fi interface in *managed* mode hands the operating system
Ethernet frames. The 802.11 MAC header — the frame control bits, the four
address fields, the sequence control — has already been stripped, and
management and control frames never reach userspace at all. Capturing in
managed mode therefore yields none of what this lab analyzes.

*Monitor mode* puts the radio into a promiscuous listen on one channel and
delivers whole 802.11 frames, usually prefixed with a radiotap header the
driver adds to carry signal strength and channel.

One radio hears one channel at a time. To see a network on channel 36 and
another on channel 6, either capture twice or hop channels — and understand
that hopping means missing frames on every channel you are not currently on.

## macOS

Monitor mode works with the built-in adapter. Note that **enabling it
disconnects the Mac from Wi-Fi**, so the capture host cannot also be the
client under observation -- use a second device you own as the client.

First find the interface and the channel the target network is actually on:

```sh
networksetup -listallhardwareports                 # Wi-Fi is usually en0
system_profiler SPAirPortDataType | grep -i channel
```

### Preferred: airportd

The `airport` utility was removed in recent macOS versions. Its replacement
for this purpose is the `sniff` verb on `airportd`, which pins the channel
and captures in one step.

The channel argument is **band-qualified with a width**, not a bare number:
`2g6/20` means channel 6 in the 2.4 GHz band at 20 MHz, `5g100/160` means
channel 100 in the 5 GHz band at 160 MHz. A bare channel number is rejected.

```sh
sudo /usr/libexec/airportd en0 sniff 2g6/20     # 2.4 GHz, channel 6
sudo /usr/libexec/airportd en0 sniff 5g100/160  # 5 GHz, channel 100
```

Stop with Ctrl-C. The pcap is written to `/tmp/airportSniffXXXXXX` owned by
root, so copy it out before analyzing:

```sh
ls -lt /tmp/airportSniff*
sudo cp /tmp/airportSniff* ./captures/my-lab.pcap
sudo chown $(whoami) ./captures/my-lab.pcap
```

If the interface stays associated (`ifconfig en0` still shows an `inet`
address) then monitor mode did not engage and the command failed -- check
its output rather than looking for a capture file that was never written.

### Alternative: Wireless Diagnostics

Hold Option, click the Wi-Fi icon, choose **Open Wireless Diagnostics**, then
**Window > Sniffer** from the menu bar. This one lets you set channel width
as well as channel, which matters on 5 GHz.

### Alternative: tcpdump

```sh
# -I requests monitor mode, -y sets the radiotap link type.
sudo tcpdump -I -i en0 -y IEEE802_11_RADIO -w lab-capture.pcap
```

This captures on whichever channel the interface is parked on, so pin the
channel with one of the methods above if you need a specific one.

## Linux

```sh
# Identify the interface and confirm the driver supports monitor mode.
iw dev
iw list | grep -A 8 "Supported interface modes"

# Switch to monitor mode.
sudo ip link set wlan0 down
sudo iw wlan0 set monitor control
sudo ip link set wlan0 up

# Pin a channel (must match the AP under test).
sudo iw wlan0 set channel 6

# Capture.
sudo tcpdump -i wlan0 -w lab-capture.pcap

# Restore afterwards.
sudo ip link set wlan0 down
sudo iw wlan0 set type managed
sudo ip link set wlan0 up
```

`airmon-ng start wlan0` does the same thing and additionally stops the
processes (NetworkManager, wpa_supplicant) that otherwise fight the
interface for control.

## Wireshark

Wireshark captures the same frames with monitor mode enabled in the capture
options. Useful display filters while exploring, before running the analyzer:

| Filter | Shows |
|---|---|
| `wlan.fc.type == 0` | Management frames |
| `wlan.fc.type == 1` | Control frames |
| `wlan.fc.type == 2` | Data frames |
| `wlan.fc.type_subtype == 0x08` | Beacons |
| `wlan.fc.type_subtype == 0x0c` | Deauthentication |
| `eapol` | The four-way handshake |
| `wlan.rsn.akms.type == 8` | Networks offering SAE (WPA3) |
| `wlan.rsn.capabilities.mfpr == 1` | Networks requiring PMF |

## Capturing a four-way handshake

The handshake only happens when a client joins, so either:

- connect a client while the capture is running, or
- disconnect and reconnect a device you own (toggling Wi-Fi off and on is
  enough, and needs no deauthentication frames at all).

Deauthenticating your own client to force a reconnect is the technique an
attacker uses, and it works on any network without PMF. It is worth
performing once against your own isolated AP to see the effect; there is no
reason to do it any other way, and `wifi/synth.py` already contains a
synthetic version of that exact sequence.

## Sanity checks before analyzing

```sh
# Frame count and link type. Expect LINKTYPE_IEEE802_11_RADIO (127).
capinfos lab-capture.pcap

# Confirm 802.11 headers survived, rather than Ethernet frames.
tcpdump -r lab-capture.pcap -c 5 -e

# Then run the analyzer.
python -m wifi analyze lab-capture.pcap
```

If the analyzer reports zero management frames, the capture was almost
certainly taken in managed mode and only data frames survived.

## Anonymizing a capture before sharing

A raw capture contains the MAC address of every device in range, which is
why the sample in this repository is synthetic rather than real. If you need
to share a genuine capture, rewrite the addresses first — for example with
`tcprewrite --enet-smac/--enet-dmac`, or by rewriting them with scapy — and
check what is left before publishing it.
